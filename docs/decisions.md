# 결정과 이유

지금까지 정한 것과 그 이유를 한곳에 모은다. 결정이 바뀌면 이 문서를 고치고, 바뀐 날짜와 이유를 적는다.
자세한 과정은 [기록](records/README.md)에 있다.

| 무엇을 | 어떻게 정했나 | 이유 | 정한 날 | 근거 |
|---|---|---|---|---|
| 만들지 말지 | 만든다 | 손으로 답을 만들어 보니 리드가 예측하기 어려운 구체적인 결과가 나왔다 | 2026-09-15 | [스파이크 보고](records/2026-09-15-spike-report.md) |
| 답의 형태 | 숫자(집계)와 원문(인용)을 함께 준다 | 키워드 검색만으로는 크게 놓치고, 숫자만으로는 무엇을 지적했는지 알 수 없다 | 2026-09-15 | [스파이크 보고](records/2026-09-15-spike-report.md) |
| MCP의 어떤 기능을 쓸지 | 핵심 기능은 Tool로만 만든다 | AI 앱마다 Resource와 Prompt를 보여주는 방식이 달랐다. Tool은 어디서나 같게 동작했다 | 2026-10-01 | [MCP 설계 판단 기준](records/2026-10-01-mcp-design-criteria.md) |
| 구현 언어 | Python (`mcp` 2.2.0) | SDK가 성숙했고 스파이크의 분석 코드를 이어 쓸 수 있다. 팀에는 새 언어지만 도전으로 본다 | 2026-10 초 | |
| 미션 범위 | 6개 전부. 첫 미션은 자바 자동차 경주 | 스파이크로 데이터와 비교 기준이 이미 있다 | 2026-10 초 | |
| 배포 | 웹을 염두에 둔다. 최종 확정은 10월 말. 그때까지 개발은 로컬 실행(stdio)으로 한다 | 리드가 설치 없이 쓰는 것이 우선이다. 다만 도구가 쓸 만한지부터 확인한다 | 2026-10-06 | [도구 명세](tool-spec.md) 7번 |
| 첫 도구가 답할 질문 | "이 미션에서 리뷰어들이 반복 지적한 것은?" | 리드 활동 시간의 대부분이 "이전 미션 리뷰" 수업 자료 준비와 미션 사전 안내에 들어갔다. 둘은 범위만 다른 같은 질문이다 | 2026-10-07 | [지원 질문 뽑기](records/2026-10-06-lead-questions.md) |
| 스터디를 구분하는 방법 | 질문하는 쪽이 GitHub ID 목록을 넘긴다 | PR 제목의 스터디명은 붙이지 않은 PR이 많다. 명단을 서버에 저장하면 관리할 것이 늘어난다 | 2026-10-07 | [도구 명세](tool-spec.md) 3번 |
| 리뷰를 주제로 나누는 방법 | 키워드 사전으로 시작한다. 분류와 도구를 나눠 두고 분류는 나중에 개선한다 | 지금 바로 되고, 비용이 없고, 결과가 매번 같다. 나눠 두면 분류를 바꿔도 도구를 다시 만들지 않는다 | 2026-10-07 | [도구 명세](tool-spec.md) 2번 |
| 작업 순서 | 명세와 검증 기준을 먼저 쓰고, 테스트로 옮긴 뒤 구현한다 | AI에게 구현을 맡길 때 "다 됐다"를 확인할 기준이 필요하다 | 2026-10-07 | [도구 명세](tool-spec.md) 8번 |
| 데이터를 저장소에 올릴지 | 올리지 않는다. 수집 명령으로 다시 만든다 | 원본이 크고(미션 하나에 17MB), 공개 PR이라 누구나 다시 받을 수 있다 | 2026-10-07 | [도구 명세](tool-spec.md) 5번 |
| 기록에 실제 사람을 적을지 | GitHub ID와 이름은 가리고 PR 번호만 남긴다 | 원본은 공개돼 있지만, 누가 어떤 지적을 받았는지 모아 정리한 글은 무게가 다르다 | 2026-10-07 | [기록](records/README.md) |

아직 정하지 않은 것은 [도구 명세](tool-spec.md) 9번에 있다.
