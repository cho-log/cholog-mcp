## 1. 오늘 무엇을 했나

### 배경

초록스터디 리드를 돕는 MCP 서버를 만들기로 했습니다. 아이디어는 이렇습니다.

> 리드: "이 미션에서 스터디원들이 자주 실수한 지점이 뭐야?"
> → 서버가 과거 PR·리뷰 기록을 뒤져서 답변

그런데 **설계를 시작하기 전에 확인해야 할 게 있었습니다.** 과거 리뷰 기록에서 실제로 쓸만한 정보가 나오는지 아무도 모르는 상태였거든요. 이걸 모르는 채로 명세를 쓰면 *만들 수 없는 기능*을 정의하게 됩니다.

### 방법: 수동 스파이크

MCP 서버를 만들지 않고, **사람이 손으로 서버 역할을 흉내 내봤습니다.**

1. 미션 1개 선정 (자바 자동차 경주, PR이 가장 많음)
2. PR과 리뷰 코멘트를 전부 내려받음
3. 3개 질문을 던지고 답을 만들어봄
4. **그 답이 "경험 있는 리드가 이미 아는 수준"을 넘는지 평가**

4번이 핵심 판정 기준이었습니다.

| | 예시 |
|---|---|
| 넘지 못함 (실패) | "많은 스터디원이 객체 분리를 어려워함" (리드라면 다 아는 얘기) |
| 넘음 (성공) | "140명 중 81명이 난수를 추상화하지 않았고, 추상화한 59명 중 31명은 중간에서 멈췄다" |

## 2. 결과

### 데이터 규모

| 항목 | 값 |
|---|---|
| 대상 레포 | `next-step/java-racingcar-simple-playground` |
| PR | 215개 (2024.04 ~ 2026.09) |
| 리뷰 코멘트 | 4,855개 (리뷰어 2,940 / PR 작성자 본인 1,915) |
| 리뷰받은 PR | 173개 |
| PR당 코멘트 중앙값 | **25개** |
| 참여 리뷰어 | 74명 |
| 총 분량 | 약 96만 자 |

데이터 밀도는 충분했습니다. PR당 리뷰가 2~3개 수준이었다면 여기서 접었을 겁니다.

### 판정: 통과

3개 질문에 답을 만들었고, 아래처럼 **리드가 예측하기 어려운 구체적 결과**가 나왔습니다.

**① 리뷰가 어디에 몰리는지**

`Car.java` 한 파일에 리뷰가 집중됩니다. 코멘트 있는 PR 173개 중 **134개(77%)**에 `Car.java` 리뷰가 달렸습니다. 이 미션의 난이도가 단일 도메인 객체 설계에 걸려 있다는 뜻입니다.

**② 예상과 다른 개념 분포**

```
테스트 용이성(난수 분리)   61%  ← 실질적 1위
인터페이스 / 추상화        40%
매직넘버 / 상수화          37%
원시값 포장 / 일급 컬렉션   27%  ← 우테코 간판 개념인데 하위권
```

일급 컬렉션이 하위권이라는 건 자료 배분을 다시 볼 근거가 됩니다.

**③ 학습자들이 어디서 멈추는지**

난수 처리를 다룬 PR 140개를 분류한 결과:

```
난수 추상화 없음              81개 (58%)
난수 추상화 있음              59개 (42%)
  └ 그런데도 다른 곳에 raw random 잔존   31개
```

**추상화를 했다고 끝이 아니라, 한 번 성공한 사람의 절반 이상이 중간에서 멈춥니다.** 이건 리드가 "다들 어려워한다" 수준으로만 알고 있던 걸 구체적 지점으로 바꿔줍니다.

**④ 리뷰어들의 조언이 정면으로 갈리는 지점**

같은 문제에 대해 리뷰어마다 반대되는 조언을 합니다.

| 쟁점 | A 입장 | B 입장 |
|---|---|---|
| 난수 분리 정도 | "더 분리하라" (PR#183, #199) | "과한 분리다" (PR#123, #113) |
| 게임 규칙을 `Car`가 알아야 하나 | "알아야 안전하다" (PR#116) | "몰라야 한다" (PR#100) |
| 난수 생성기를 테스트해야 하나 | "하지 마라" (다수) | "가장 중요한 부분이다" (PR#187) |

**리드에게 이게 제일 유용할 수 있습니다.** 정답이 없는 지점을 미리 알면, 스터디원이 물었을 때 "정답은 없고 이런 트레이드오프가 있다"고 답할 수 있습니다. 리뷰어를 모집할 때 온도를 맞추는 데에도 쓰입니다.

**⑤ 리뷰 밀도 편차**

리뷰어마다 PR당 코멘트 수가 **10.8개 ~ 48개로 4.4배** 차이납니다. 리뷰어에게 어느 정도를 기대해야 하는지 기준점이 없던 문제입니다.

## 3. 덤으로 알게 된 것 (설계에 직접 반영)

스파이크를 하지 않았으면 몰랐을 제약 3가지입니다.

**제약 1. 파일 목록만으로는 구조를 판정할 수 없다**

인터페이스 파일이 존재해도 내부에서 직접 객체를 생성해 주입이 안 되는 사례가 다수입니다. 파일 이름만 세면 "성공"으로 잘못 집계됩니다. → 코멘트 본문과 코드 조각을 함께 봐야 합니다.

**제약 2. 한국어 키워드 검색만으로는 크게 놓친다**

같은 지적이 비유·질문·키워드 제시 등 여러 방식으로 표현돼서, 키워드로 세면 실제의 1/4 수준까지 떨어집니다. → **숫자(집계)와 원문(인용)을 함께 제공**하는 방식이 필요합니다.

**제약 3. 조회 단위는 "PR"이 아니라 "미션 × 주제"**

한 PR에 리뷰어는 거의 항상 1명입니다(173개 중 163개). 대신 미션 전체를 가로지르면 74명의 관점을 비교할 수 있습니다.

기타: GitHub API를 매번 호출하면 안 되고(215개 PR 수집에 430회 호출) 미리 받아 저장해야 합니다. 규모상 무거운 검색 엔진 없이도 될 것으로 보입니다.

### 이번 회의에서 정하면 좋을 것

1. **개발을 진행할지.** 저는 진행 의견입니다.
2. **범위.** 미션 6개 전부인지, 자바 미션부터 시작할지
3. **사용 형태.** 리드가 어떻게 쓰게 할지 (각자 설치 / 공용 서버 / 디스코드 봇 등)
4. **역할 분담.** 운영진 3명 모두 MCP 개발 경험이 없는 상태입니다

### 참고

- 수집한 데이터와 분석 스크립트는 `mcp/spike/`에 있습니다. 다른 미션에도 그대로 돌려볼 수 있습니다.
- 미션마다 패턴이 다른지는 아직 확인하지 않았습니다. 명세 초안이 나온 뒤 다른 미션으로 한 번 더 검증해볼 수 있습니다.
